I build small tools and write down how they work

Mostly things I wanted to exist and couldn't find, or could find only behind a subscription. Each one gets a write-up here — what the problem actually was, what the working version does, and where it falls short.

The write-ups are the point as much as the tools are. Plenty of projects get a one-line description and a repository link, which tells you nothing about why a decision was made or what broke on the way. I'd rather record the reasoning while it's still fresh, including the parts that turned out wrong.

Projects

  • Indexer

    A self-hosted replacement for paid instant-indexing services. Submits pages to Google and IndexNow, watches sitemaps for real changes, audits pages that refuse to index, and tracks coverage over time.

How I pick what to build

Two rules, both learned the boring way. The first is that the tool has to be something I'll use every week. Anything built for a hypothetical user gets abandoned somewhere around the second refactor, when the interesting problem is solved and only the tedious part is left. Needing it myself is what carries a project through that stretch.

The second is that it has to be a thing I can finish. Not a platform, not a framework, not a startup — a program that does one job and then stops. The indexer below reads sitemaps, submits URLs, and reports what happened. It will never grow a login screen or a pricing page, and being certain of that from the start changes every design decision for the better.

The consequence is a set of small, sharp tools rather than one large one, and write-ups that are longer than the code deserves. That trade suits me. Code without the reasoning behind it is just a diff, and six months later I can't reconstruct why I chose one approach over the other from the source alone.
